# Pipeline Developer Academy

## Purpose

Pipeline Developer Academy is a private, source-grounded ownership program for this repository. It is designed to take a developer with basic TypeScript and software-engineering familiarity to safe production ownership of a behavioral-health admissions platform.

This is not a generic Next.js course. It teaches the application through the actual referral, document, extraction, assessment, decision, EHR, identity, security, database, and recovery paths that operators depend on.

## What the web application provides

The private route is `/academy`. It contains five integrated views:

1. **Curriculum:** 10 tracks, 36 modules, 144 activities, and more than 100 guided hours.
2. **Journeys:** golden execution paths that identify runtime, source owner, invariant, outcome, and failure question.
3. **Repository:** a generated searchable atlas of every maintained code, test, infrastructure, asset, and documentation file.
4. **Labs:** one applied engineering exercise per module with explicit evidence and acceptance criteria.
5. **Mastery:** track progression, competency gates, evidence counts, repository coverage, and capstone readiness.

Every module follows the same learning loop: learn the model, trace the current source, complete an applied lab, and pass a checkpoint. Source-trace and lab completion require written evidence.

## Access and progress

The server returns not-found unless the authenticated principal exactly matches `PIPELINE_ACADEMY_OWNER_EMAILS` or `PIPELINE_ACADEMY_OWNER_ENTRA_OBJECT_IDS`. Production has no fallback owner. Local mock mode may use the configured mock identity.

Progress is stored through the versioned per-user workspace-state store when PostgreSQL or the allowed local developer store is available. Saves use optimistic revisions and merge independent completion/evidence changes after a conflict. Browser storage provides offline/local fallback and hydration recovery; it is not the production system of record.

The Academy never reads or writes referral, assessment, packet, clinical, or EHR records.

## Safety rule

Academy evidence must never contain PHI, client identifiers, packet text, client-bearing filenames, credentials, secrets, tokens, production connection strings, or copied production records. Use synthetic identifiers and redacted architecture examples.

## Authority model

- `lib/academy/academy-curriculum.ts` owns tracks, modules, activities, prerequisites, labs, checks, and competencies.
- `lib/academy/academy-journeys.ts` owns golden end-to-end paths and invariants.
- `lib/academy/academy-atlas.generated.json` maps maintained files to learning owners and is generated by `scripts/academy-atlas.mjs`.
- `docs/academy/academy-registry.json` stores reviewed thresholds and fingerprints without duplicating lesson prose.
- The implementation itself is always authoritative over the Academy.

## Commands

```bash
npm run academy:atlas:check
npm run academy:check
npm run academy:route:check
npm run academy:certify
```

After reviewed source, curriculum, or repository-topology changes:

```bash
npm run academy:refresh
git diff -- lib/academy/academy-atlas.generated.json docs/academy/academy-registry.json
npm run academy:certify
```

Do not refresh fingerprints merely to make a failing check green. First review changed source anchors, learning ownership, journey invariants, exercises, and checkpoints.

## Completion versus mastery

An activity completion means the learner recorded the required work. It does not certify production authority. Mastery requires source-backed recall, applied evidence, safe decisions under failure and concurrency, independent review where required, and teach-back. The owner capstone is the final integrated proof.

See [ENTERPRISE_ACADEMY_STANDARD.md](ENTERPRISE_ACADEMY_STANDARD.md) for maintenance, review, and evidence rules.

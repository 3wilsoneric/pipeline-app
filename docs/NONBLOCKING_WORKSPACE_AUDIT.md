# Non-blocking referral workspace: implementation plan

Status: corrected against `origin/main` at `24f14ae0` (2026-09-24). Intake → Chart navigation, Decision drafting and independent paperwork updates during a checklist save, Decision and Assessment draft ownership across workspace tabs, and local Assessment Previous/Next section movement are implemented locally on this branch; the other work below remains planned. Nothing in this branch has been deployed.

## Outcome and safety rule

Moving among Chart, Intake, Assessment, Decision, Files, and Activity should not wait for an unrelated network save. Editing should remain possible while another field saves. The exception is an operation where a second or conflicting command could cause harm: signing, sending an email, recording a final decision, changing accounts, and leaving a workspace with no recoverable copy. A failed save stays visible, retryable, and accurately labeled; a local-only copy must never be called server-saved.

Internal navigation is different from closing the tab or switching identity. A verified local recovery copy can release an internal navigation while server sync continues. If both local persistence and server sync fail, the user may move among mounted views only if the live draft remains owned by the workspace shell; closing or switching identities still requires a warning or successful save. Pending files need recoverable blobs, not just their names.

## Implementation sequence

1. **Lock down the behavioral contract with focused tests.** Reproduce a slow save, a 500 response, offline mode, rapid tab switching, and two quick Decision actions. Assert that the second action is neither silently discarded nor sent twice. Include a pending file and a refresh, because file names alone are not recovery. Reuse the existing save/recovery suites.
2. **Make internal tab changes durable but non-blocking.** Use the existing referral-scoped recovery store. For Intake, await the local-copy acknowledgement, not the server queue. For Assessment, keep its unsynced answer state/queue alive across view changes before releasing its navigation wait. Surface a workspace-level `Saving`, `Saved on this device`, or `Could not save — Retry` status that follows the user across tabs. Do not clear dirty state until the matching server version is confirmed.
3. **Narrow busy scopes without dropping actions.** Decision controls may accept draft input during another save, but command submissions must enter a queue or show a specific pending state. Make checklist pending/error per requirement; retain version/conflict handling. Assessment Previous/Next and read-only review may move during unrelated autosave, while sign/begin/schedule transitions keep only their necessary guards. Then remove redundant Intake Done/dialog-close locks.
4. **Harden recovery and exits.** Bound the initial recovery wait without permitting late overwrite; distinguish internal navigation from browser exit/account switch. Keep the existing identity guard and unload warning while server sync is outstanding. Provide an explicit retry path for a failed server save without replaying non-idempotent actions blindly.
5. **Verify the affected workflows locally.** Run focused unit/integration and e2e cases for Intake → Assessment, Assessment ↔ Chart/Files/Decision, schedule/review, Decision checklist/record, offline/retry, file recovery, and account switch. Inspect the affected mobile and desktop controls and keyboard focus. No unrelated refactor or deployment is part of this work.

## Completion criteria

- Internal tabs respond without waiting on a healthy but slow server save; an unsynced edit survives tab switching and refresh when local persistence succeeds.
- A local-write failure is visible, and neither a failed nor an ambiguous server write is represented as saved. If every persistence path fails, the live draft remains available and leaving the browser/identity is warned.
- No dropped, duplicated, or stale-version Decision, schedule, signature, email, or file mutations. PHI stays scoped to the same authenticated principal and referral.
- The current save/recovery/concurrency tests pass, plus the focused failure-path cases above. Existing layout and workflow semantics are unchanged apart from the intended removal of unnecessary waits.

Known ceiling: no browser app can guarantee recovery if server, browser storage, and the open tab all fail simultaneously. In that case the UI must say so plainly and must not imply a successful save.

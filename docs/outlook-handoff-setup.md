## Assessor flow after activation

Assessors are offered **Connect your Outlook** when they enter Pipeline, before preparing a handoff. **Connect later** dismisses the prompt for that tab's session and lets them keep working; it never clears a connection. They can connect near the top of **Settings** or before saving their first Outlook draft. The prompt does not interrupt another open dialog and does not appear during the demo hold or delegated assessor sessions. Connecting only verifies the assessor's own mailbox; it does not create a draft or send mail. Connected settings show status without a disconnect control.

MSAL manages the Outlook cache in local storage, allowing the same browser to restore access after a tab is closed or reopened. Cached credentials and Microsoft SSO are tried silently for the signed-in Pipeline email, and the server verifies the mailbox before showing Connected. Pipeline adds no expiry, disconnect flag or automatic cache reset to this connection; failed restoration leaves the cache available for recovery. Whole-browser restarts depend on Microsoft's session and “Stay signed in” choice; expiry, revoked consent, cleared browser data, browser privacy restrictions, or another device may require reconnection. Pipeline's existing explicit Microsoft sign-out is preserved: MSAL clears shared sign-in cache on that path. Removing a Pipeline account or its authorized role denies connection and draft APIs even with a cached Outlook token. Existing drafts stay in Outlook. This uses browser-managed delegated access; retaining a link independently of browser storage or Microsoft sign-out would require a separately designed server-side OAuth credential store. Revisit that design if those become release requirements; the current implementation cannot promise persistence until account deletion alone.

In **Finish & send → Review handoff**, enter or confirm the planned admit date first. A date is required and is saved to the workspace, where it also appears in Decision, and automatically populates the email. Then confirm the client summary, check the complete admission packet, and verify the To/Cc recipients in separate dialogs. Each dialog has one primary next action. The email preview opens only after those checks; recipient edits clear the authorization check. The preview uses the Alamo Health Management logo and contains no Pipeline branding. Message editing is available from the preview. Connect the Outlook mailbox matching your authenticated Pipeline email, then choose **Save to Outlook Drafts**. Pipeline saves the Alamo-branded message, every uploaded file and the generated client data sheet as ordinary attachments directly in that mailbox's Drafts folder and opens it in Outlook. The assessor reviews and presses Send in Outlook; replies go to that assessor.

Once an Outlook draft exists, **Continue with Outlook draft** reopens it directly without repeating the setup dialogs. Before a draft exists, review confirmations remain local to the current visit; recipients and message edits remain saved. A replacement draft requires fresh review of the current sources. Closing a modal does not confirm it or complete the demo.

Each assessor connects their own mailbox. Eric's Outlook.com account can be used for his own synthetic rehearsal; it cannot place drafts into other assessors' mailboxes. Work, home-tenant guest and personal Microsoft accounts are supported. Pipeline's sign-in tenant and access policy remain unchanged. Microsoft may require the assessor's organization to approve the connection.

The draft persists across leaving, refreshing and returning. Preparing it does not complete or lock the assessment. After sending from Outlook, choose **Check sent status**. Pipeline checks the actual message's sent timestamp, reviewed recipient audience, every attachment’s actual bytes, assessment version, decision and file inventory before completing the handoff. Sent status does not prove recipient delivery or reading. Missing or altered attachments, changed recipients, and source changes require review before the handoff can be recorded as complete. Already-sent attachments cannot be recalled. An uncertain creation response retains its reservation and recovers the existing message instead of sending or creating a duplicate.

The composer displays the saved draft's To/Cc, mailbox and file count. To change the prepared packet or recipients, remove the draft and review a replacement. Removal deletes an unsent Outlook draft; it cannot withdraw attachment copies already sent. An already-sent email cannot be recalled. Older Graph drafts without saved To/Cc still reopen in Outlook; their combined recipient set is not presented as an exact To/Cc split.

## One-time setup for the Pipeline owner

1. Register a separate **Pipeline Outlook Drafts** public application, supporting work/school and personal Microsoft accounts (`AzureADandPersonalMicrosoftAccount`). Add the SPA redirect `https://alamo-pipeline.com/outlook-auth.html`, or the approved canonical origin and base path. Request only Microsoft Graph **delegated Mail.ReadWrite** and **User.Read**. No client secret, application mail permissions or Mail.Send grant is required for assessor drafts.
2. Set server runtime `PIPELINE_OUTLOOK_CLIENT_ID` to that application's client ID. The authenticated connection and draft-status APIs supply this public identifier to the browser; it is not a build-time sign-in configuration. The separate MSAL client uses `common`, MSAL-managed local storage and a static callback. Installed MSAL v4's parent window consumes the callback hash. Only `/outlook-auth.html` permits same-origin framing for silent restoration, with scripts and other resources disabled and caching prohibited; application pages still reject framing. Revisit this callback when upgrading MSAL's major version; v5 has different redirect-bridge requirements.
3. Configure the approved recipient-domain allowlist. The assessor attachment workflow does not need an Admissions service sender, application Mail.Send, or a recipient verification-code service. Preserve any existing service credentials only for legacy deliveries and links; they are not prerequisites for new assessor drafts.
4. Verify the application’s HTTPS origin, normal sign-in/session configuration, Blob storage and PostgreSQL migration 0042. New drafts reuse its persisted manifest/audit records without exposing a recipient download route. Recipients open the attached files in their email client; no code or Pipeline account is involved. Do not broadly allow personal domains just to conduct a sample.
5. Complete the release checks and a synthetic rehearsal covering connection, draft save/reopen, every attachment, onward sending, inbox receipt and status reconciliation. Verify the files received, including a large attachment. Provider acceptance alone is insufficient. Owner authorization for production activation is recorded above; an assessor still completes Microsoft's mailbox consent when connecting.

The existing production policy allows `aaahealthservices.com`, `aaasanpablo.com`, `ahmsantaclarita.com`, `ahmturlock.com`, `victoriashousesf.com`, `jcwallacehouse.com` and `alamo-pipeline.com`. Do not replace it with a broad personal-email domain for a rehearsal. Verify the runtime flags, early Outlook connection prompt and a mailbox-owned attachment draft after release. To pause new handoffs, deploy with `meet_client_activation=disabled`; retain packet records and existing draft recovery. Use the known prior image/configuration for a code rollback.

Mailbox binding uses the Microsoft Graph profile and Pipeline's authenticated identity, never an editable contact field or a supplied address. Home-tenant and personal mailbox IDs may differ from the Pipeline identity's ID; the authenticated email must match in that case. New packets pin both the Pipeline owner and the actual Graph mailbox ID. Subsequent checks/removal require both. Delegated assessor sessions cannot connect as the assessor. Tokens are never persisted in packet records, returned in API responses or logged.

## Recovery and rollback

Small files use Graph file attachments; larger files use resumable upload sessions with chunks below 4 MiB. ETags pin uploaded source bytes; stored hashes verify Outlook attachments, including after a lost upload response. Preparation starts with an unaddressed placeholder, and only adds the final message and To/Cc after every file is verified. A persisted operation lease prevents simultaneous preparation, checking and removal across tabs/replicas. Interrupted preparation retains its reservation and resumes the same message.

Microsoft’s attachment and mailbox message-size limits still apply. A size refusal preserves the files and partial draft and reports the problem; it never silently omits a file or substitutes a link. Separate emails may be necessary in Outlook. Background preparation is not implemented: revisit it if measured preparation approaches the five-minute request deadline.

Existing Outlook drafts remain recoverable. Older packet records without a separate mailbox ID use their original owner ID; new records pin both IDs. Older drafts without saved To/Cc reopen in Outlook without inventing a recipient split. New attachment state is additive JSON in the existing packet store; no new database migration is required. Legacy linked drafts retain their original link checks and download routes. Attachment-only records cannot issue verification codes, renew links or expose downloads.

The proposed inbox-forwarding transport was never deployed and has been removed from this candidate. There are no emailed-draft lifecycle handlers to maintain. Keep sending disabled during rollback, preserve packet/audit records, and retain the existing Graph Drafts recovery controls. The local packet adapter supports one process; PostgreSQL owns production locking.
